## Running Migrations

### Using Supabase CLI (recommended)
```bash
# Install Supabase CLI
npm install -g supabase

# Link your project
supabase link --project-ref YOUR_PROJECT_REF

# Push all migrations
supabase db push

# Or run a single file directly
psql "postgresql://postgres:YOUR_PASSWORD@db.YOUR_PROJECT_REF.supabase.co:5432/postgres" \
  -f supabase/migrations/001_enums_and_extensions.sql
```

### Using psql directly
```bash
# Run all in order
for f in supabase/migrations/*.sql; do
  echo "Running $f..."
  psql "$DATABASE_URL" -f "$f"
done
```

## Schema Overview

```
territories
    └── users (territory_id)
            ├── manager_id (self-ref)
            ├── user_device_tokens
            └── clients (assigned_salesperson_id)
                    ├── client_tags → client_tag_definitions
                    ├── client_visits
                    └── orders (client_id)
                            ├── order_items → products
                            ├── otp_logs
                            ├── order_status_history
                            └── returns
                                    ├── return_items
                                    └── credit_notes
                                            └── credit_note_applications

products
    ├── categories (hierarchical, parent_id self-ref)
    ├── brands
    ├── schemes
    └── product_price_history

notifications (per user)
```

## Key Design Decisions

### 1. Price Snapshotting
`order_items` stores `product_name`, `sku_code`, `unit_price`, and `gst_percent` **at the time of order**. This ensures historical orders are never affected by future price changes.

### 2. OTP in Redis, Not Postgres
The actual OTP value (bcrypt hash) lives in Redis with a 10-minute TTL. `otp_logs` is a permanent audit trail of **events** (sent, verified, expired) — it never stores the OTP itself.

### 3. Immutable OTP Logs
No `UPDATE` or `DELETE` RLS policies exist on `otp_logs`. The application enforces append-only behavior. This satisfies audit requirements.

### 4. Order Number Sequence
Format: `AG-YYYY-NNNNN` (e.g., `AG-2026-00001`). Generated by a Postgres trigger using a global sequence `order_number_seq`. Resets annually if you truncate and recreate the sequence (optional).

### 5. Client Stats Denormalization
`clients.total_orders` and `clients.total_revenue` are maintained by a trigger on `orders`. This avoids expensive COUNT/SUM queries for every client list load. Accept eventual consistency vs. join complexity trade-off.

### 6. Offline-First Support
`orders.local_draft_id` stores the WatermelonDB local ID so the API can deduplicate if the same draft is synced multiple times (idempotency key). `orders.created_offline` is a flag for analytics.

### 7. Soft Deletes
`users` and `clients` use `deleted_at` instead of hard deletes. This preserves referential integrity in historical orders. Products use both `is_active` and `deleted_at`.

### 8. RBAC via RLS
Row Level Security is enforced at the database layer — not just the API. Even if a route middleware is bypassed, Supabase will return empty results or throw an error if the user lacks permission.

## Indexes Summary

Performance-critical indexes created:

| Table | Index | Purpose |
|-------|-------|---------|
| `users` | `(role) WHERE deleted_at IS NULL` | Role-based user lookup |
| `clients` | GIN full-text on `business_name` | Client search |
| `clients` | `(mobile_primary)` | OTP lookup |
| `products` | GIN full-text on `name + description` | Product search |
| `products` | `stock_qty WHERE ≤ threshold` | Low stock alerts |
| `orders` | `(salesperson_id, created_at DESC)` | Dashboard queries |
| `orders` | `(status, delivery_date)` | Warehouse queue |
| `otp_logs` | `(mobile_sent_to)` | OTP verification |
| `notifications` | `(user_id, is_read)` | Unread notification badge |
